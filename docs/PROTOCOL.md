# Протокол CSLVPN v1

Документ описывает проводной протокол между клиентом и ретранслятором.
Реализация: `internal/proto` (формат), `internal/crypto` (ключи), `internal/relay`
(сервер), `internal/client` (клиент). Любая совместимая реализация может быть
написана по этому тексту.

## 1. Транспорт и кадрирование

Один и тот же формат кадра используется поверх **UDP** и **TCP**. По умолчанию
оба слушателя занимают один и тот же порт (7777), поэтому выбор транспорта не
меняет адрес сервера.

```
+--------+--------+------------------+
| u16    | u8     | body             |
| length | type   | (length-1 байт)  |
+--------+--------+------------------+
   length = 1 + len(body), big endian, максимум 65536
```

* **UDP**: один кадр — одна датаграмма. Потери и перестановки допустимы,
  доставку обеспечивают протоколы внутри туннеля.
* **TCP**: кадры идут подряд в одном потоке; порядок и доставку гарантирует
  транспорт, перестановок нет.

Кадры, начиная с `FRAME_WELCOME`, **всегда** шифруются; служебные кадры
рукопожатия (`HELLO`, `CHALLENGE`, `AUTH_PROOF`, `AUTH_OK`, `AUTH_ERR`) идут
открытым текстом (они не содержат секретов — см. §3).

## 2. Типы кадров

| Код | Имя | Направление | Шифрование | Назначение |
|----:|-----|-------------|:----------:|------------|
| 1 | `HELLO` | C→S | нет | версия, транспорт, публичный ключ, сеть, имя |
| 2 | `CHALLENGE` | S→C | нет | публичный ключ сервера, соль |
| 3 | `AUTH_PROOF` | C→S | нет | HMAC-подтверждение пароля + завёрнутый ключ сети |
| 4 | `AUTH_OK` | S→C | нет | подтверждение сервера |
| 5 | `AUTH_ERR` | S→C | нет | код ошибки + текст |
| 6 | `WELCOME` | S→C | да | выданный адрес, префикс, MTU, id сети, флаги |
| 7 | `PEER_LIST` | S→C | да | состав сети |
| 8 | `DATA` | оба | да | `u32 dst_ip` + внутренний IP-пакет |
| 9 | `PING` | оба | да | `u64` метка времени |
| 10 | `PONG` | оба | да | эхо метки времени |
| 11 | `BYE` | оба | да | штатное завершение |
| 12 | `KICKED` | S→C | да | участник удалён администратором |

## 3. Рукопожатие

```
клиент                                                    сервер
  │ HELLO {ver, transport, flags, pub_c, nonce_c,           │
  │        network, member, want_ip}                        │
  ├────────────────────────────────────────────────────────►│
  │                                    CHALLENGE {ver, pub_s, salt}
  │◄────────────────────────────────────────────────────────┤
  │                                                        │
  │  shared = X25519(priv_c, pub_s)   (== X25519(priv_s, pub_c))
  │  transcript = SHA256("cslvpn/v1/handshake" || HELLO || CHALLENGE || shared)
  │
  │  pwKey  = PBKDF2-SHA256(password, SHA256("cslvpn/v1/network-salt/"||network), 200000, 32)
  │  proof  = HMAC-SHA256(pwKey, "cslvpn/v1/client-proof" || transcript || shared)
  │  kwKey  = HKDF-SHA256(ikm=shared, salt=salt, info="cslvpn/v1/keywrap", 32)
  │  blob   = AES-256-GCM(kwKey, seq=0, type=1, "cslvpn-key" || pwKey)
  │ AUTH_PROOF {proof[32] || blob}                          │
  ├────────────────────────────────────────────────────────►│
  │                            (сервер проверяет proof и распаковывает pwKey,
  │                             затем находит/создаёт сеть и выдаёт адрес)
  │                                        AUTH_OK {HMAC-SHA256(pwKey, "cslvpn/v1/server-proof"||transcript||shared||proof)}
  │◄────────────────────────────────────────────────────────┤
  │                                        WELCOME {ip, prefix, mtu, net_id, max_members, transport, gateway}
  │◄────────────────────────────────────────────────────────┤
  │  c2s, s2c = HKDF-SHA256(ikm = shared||pwKey, salt = transcript[0:16],
  │                         info="cslvpn/v1/handshake", 64) → по 32 байта
  │  дальше все кадры ≥ FRAME_WELCOME шифруются AES-256-GCM             │
```

Свойства:

* **Пароль не передаётся по сети** — передаётся только HMAC от него и ключ
  сети, завёрнутый в ключ, производный от эфемерного ECDH-секрета.
* **Forward secrecy**: `shared` эфемерный; записанный трафик нельзя расшифровать
  после компрометации пароля.
* **Взаимная аутентификация**: клиент подтверждает знание пароля (`proof`),
  сервер подтверждает его (`AUTH_OK`); при несовпадении клиент рвёт соединение.
* **Привязка к каналу**: `transcript` включает оба сообщения рукопожатия, поэтому
  подмена `HELLO`/`CHALLENGE` ломает ключи.
* **Привязка к сети**: `pwKey` зависит от имени сети, одно и то же имя+пароль в
  разных сетях даёт разные ключи.

### 3.1. Повторы (UDP)

`HELLO` повторяется клиентом до получения `CHALLENGE` (стартовый интервал
~300 мс, рост до 3 с, общий таймаут 20 с). Если сервер уже аутентифицировал
сессию и получил повторный `HELLO`/`AUTH_PROOF`, он повторяет `WELCOME` и
последний `PEER_LIST`.

## 4. Защищённый кадр

Поле `body` шифрованного кадра:

```
u32 seq (big endian, счётчик отправленных кадров, начинается с 0)
ciphertext = AES-256-GCM(key, nonce = 0x00000000 || u64 seq,
                         plaintext = body_plain,
                         aad = type || u64 seq || u16 len(body_plain))
```

* `type` в AAD исключает подмену типа кадра;
* `seq` в AAD исключает перестановку и повтор;
* для UDP приёмник держит 64-битное скользящее окно повторов; для TCP —
  монотонный счётчик (перестановок в потоке нет);
* при ошибке аутентификации кадр молча отбрасывается (счётчик `dropped`).

## 5. Данные

`DATA`: `u32 dst_ip || IPv4-пакет` (заголовок + полезная нагрузка, до MTU
туннеля, по умолчанию 1400 байт).

Маршрутизация на сервере:

1. `dst_ip` внутри `/24` **своей** сети → участнику с этим адресом;
2. `dst_ip` вне своей сети → только если сессия запросила интернет-доступ
   (`HELLO.flags & HELLO_FLAG_INTERNET`) и сервер запущен в режиме шлюза;
   пакет уходит в шлюзовой TUN и NAT-ится;
3. иначе — отбросить.

Пересылка «по адресу» гарантирует изоляцию: адрес принадлежит ровно одной
сети, а отправитель может попасть только в свою сеть.

## 6. Флаги

`HELLO.flags`:

| Бит | Имя | Значение |
|----:|-----|----------|
| 0 | `HELLO_FLAG_CREATE` | создать сеть, если её нет (аналог «Create network») |
| 1 | `HELLO_FLAG_NO_RETRY` | не заменять «зависшую» сессию с тем же именем |
| 2 | `HELLO_FLAG_INTERNET` | прошу интернет-доступ через ретранслятор |

`PEER_LIST`: `PEER_FLAG_SELF` — это я; `PEER_FLAG_INITIATOR` зарезервирован под
прямой P2P-канал.

`WELCOME`: `gateway = 1` — сервер подтвердил интернет-доступ; поле `transport`
всегда равно запрошенному транспорту (несовпадение — ошибка).

## 7. Коды ошибок (`AUTH_ERR`)

| Код | Значение |
|----:|----------|
| 1 | общая ошибка |
| 2 | неподдерживаемая версия протокола |
| 3 | сеть не найдена (или создание запрещено) |
| 4 | неверный пароль сети |
| 5 | сеть переполнена |
| 6 | участник забанен (после kick) |
| 7 | нет свободного виртуального адреса |
| 8 | сеть отключена администратором |
| 9 | сеть временно недоступна |
| 10 | имя участника уже в сети |
| 11 | некорректный запрос (в т.ч. несовпадение транспорта) |

Код 3 (`NO_SUCH_NETWORK`) клиент считает **временным** и повторяет попытки —
как в Radmin VPN, где можно ждать, пока владелец создаст сеть с известным вам
именем и паролем. Остальные ошибки, кроме 9, фатальны.

## 8. Keepalive и таймауты

* клиент отправляет `PING` каждые 10 с, сервер отвечает `PONG`;
* сервер шлёт `PING` каждые 10 с и считает участника мёртвым после 45 с
  молчания (UDP);
* для TCP сервер ставит дедлайн чтения 45 с;
* клиент переподключается с экспоненциальной задержкой 1→30 с, сохраняя
  виртуальный адрес (имя участника переиспользуется сервером).

## 9. Порты и брандмауэр

* `UDP/7777` и `TCP/7777` — на ретрансляторе (наружу открыть оба, если нужны
  оба транспорта);
* исходящие UDP/TCP на клиентах — в сторону сервера;
* `127.0.0.1:7778` — админ-API (наружу не публиковать);
* в режиме шлюза — `ip_forward=1` и MASQUERADE для `26.0.0.0/8`.
