# Журнал разработки

Хронология работы: что делалось, какие решения принимались и почему, какие
ошибки нашлись и как проверялось. Документ ведётся по ходу работы, чтобы
решения не пришлось восстанавливать по коду.

Дата работы: 2026-11-10. Ветка: `arena/6556e0e2-cslvpn`.

## Этап 0. Изучение задачи и окружения

* Изучены материалы по Radmin VPN: модель «комната по имени+паролю»,
  виртуальные адреса `26.x.x.x`, P2P с fallback на ретранслятор, AES-256,
  лимит ~150 участников, только Windows. Итог — `docs/RADMIN-VPN-ANALYSIS.md`.
* Проверено окружение сборки: Go в песочнице отсутствует, `apt` без сети,
  но GitHub Actions в репозитории работает (проверено smoke-workflow).
  Найден тулчейн Go 1.27.3 в PyPI-пакете `go-bin` — установлен локально,
  поэтому весь код проверялся локально **и** в CI.
* Проверено, что в песочнице есть `/dev/net/tun`, `netns`, `iptables` и
  sudo — значит возможен настоящий end-to-end тест, а не только юнит-тесты.

## Этап 1. Решения по архитектуре

1. **Только стандартная библиотека Go.** Ноль внешних зависимостей →
   сборка не требует сети, кросс-компиляция тривиальна, аудит проще. Всё
   нужное (AES-GCM, X25519, PBKDF2, HKDF, HMAC) есть в stdlib.
2. **Один бинарник**: `server`, `client`, `status`. Удобно для деплоя и для
   тестов (сервер и клиент — одна кодовая база).
3. **Транспорт — параметр клиента, а не сервера.** Оба листенера на одном
   порту; клиент указывает транспорт в `HELLO`, сервер сверяет с сокетом.
   Так «выбор UDP или TCP» становится проверяемым свойством, а не догадкой.
4. **Изоляция через адреса.** Каждая сеть получает свой `/24` из
   `26.0.0.0/8`; сервер пересылает только внутри `/24`, чужие адреса
   отбрасываются. Это проще и надёжнее проверок «по членству».
5. **Пароль сети никогда не идёт по проводу.** На проводе — HMAC-подтверждение
   и ключ сети, завёрнутый в ключ из эфемерного ECDH-секрета.
6. **Ретранслятор всегда** (без P2P в v1): предсказуемо работает за любым
   NAT/CGNAT; P2P — оптимизация на будущее (ROADMAP).

## Этап 2. Реализация

Порядок: протокол → крипто → сервер → клиент → CLI → админ-API → тесты →
CI → документация.

Файлы и ответственность:

| Путь | Что делает |
|---|---|
| `internal/proto` | кадрирование (длина+тип), бинарный кодировщик, сообщения |
| `internal/crypto` | PBKDF2-ключ сети, X25519, HKDF, AEAD-кадры, окно повторов |
| `internal/relay` | реестр сетей, сессии, UDP-демультиплексор, TCP-листенер, шлюз, админ-API |
| `internal/client` | link (UDP/TCP), secure (AEAD), рукопожатие, пересылка пакетов, реконнект |
| `internal/tun` | `/dev/net/tun` через ioctl, настройка адресов/маршрутов, NAT |
| `cmd/cslvpn` | CLI: `server`, `client`, `status` |

## Этап 3. Ошибки, найденные при проверке (и исправления)

Все ошибки ниже найдены **реальными запусками**, а не чтением кода.

1. **Клиент переподключался сразу после подключения.** В горутине
   «tunnel → TUN» стоял `default:` рядом с `select` по тикеру: чтение
   выполнялось постоянно, а при таймауте (UDP, 1 с) цикл не отличал
   «нет данных» от «соединение умерло». Исправлено: таймаут — это нормальное
   событие, `shutdown` вызывается только при настоящей ошибке; добавлены
   причины остановки в лог.
2. **`ip route replace default` ломал UDP-сокет туннеля.** После переноса
   default route в туннель ядро возвращало `ENETUNREACH` при записи в сокет,
   и клиент уходил в реконнект. Исправлено: перед сменой маршрута
   закрепляется `/32` до ретранслятора (`ip route get` → `via/dev`) и
   добавлено самовосстановление UDP-сокета (`ensureLocalAddr`) на случай
   потери маршрута.
3. **Интернет через сервер не работал.** Пакеты доходили до шлюзового
   TUN (видно по `ip -s link`), но ответы не находили клиента: у хоста не
   было маршрута к `26.0.0.0/8` через шлюзовой интерфейс. Исправлено:
   сервер сам добавляет `ip route replace <nat-cidr> dev <gateway-iface>`
   при включении режима шлюза.
4. **`iptables ... -o ! iface` — неверный синтаксис** (правильно `! -o iface`),
   из-за чего режим шлюза не включался. Исправлено.
5. **`-nat-cidr` без интерфейса давал пустой аргумент** (`-o ! ""`) — правило
   собиралось некорректно. Исправлено: при пустом интерфейсе `-o` не
   добавляется вовсе.
6. **Сеть нельзя было создать администратором при `-allow-create=false`.**
   Найдено тестом `TestNetworkCreationDisabled`: `CreateNetwork` шёл тем же
   путём, что и клиентский вход. Исправлено отдельным флагом `force`.
7. **Тесты UDP-клиента получали «connection refused».** Оба листенера
   поднимались на `127.0.0.1:0`, а тест обращался к TCP-адресу для UDP-клиента.
   Исправлено в тесте (в проде порт общий, поэтому проблемы нет).
8. **e2e-скрипт падал на повторных запусках** из-за оставшихся netns/veth —
   добавлена идемпотентная очистка. Также исправлена проверка «сайт поднялся»:
   `ss` не видел процесс в чужом netns, теперь ждём появления слушателя.

## Этап 4. Чем это проверено

* `go vet ./...`, `gofmt`, `go test -race ./...` — зелёные.
* `scripts/e2e-test.sh` (netns + настоящий `/dev/net/tun`):
  * клиент A (UDP) создаёт сеть, клиент B (TCP) входит в неё;
  * ping A↔B в обе стороны (0% потерь);
  * HTTP-скачивание через туннель (TCP-приложение внутри виртуальной сети);
  * клиент C в другой сети недостижим из первой (изоляция);
  * неверный пароль отклоняется с кодом `ERR_BAD_PASSWORD`;
  * админ-API отдаёт статистику и состав сети.
* `scripts/nat-test.sh`: клиент с `-internet` получает default route в
  туннель, скачивает страницу с узла, который доступен **только** через
  ретранслятор (NAT), и адрес клиента не «протекает» наружу.
* GitHub Actions: сборка и тесты на каждый push + e2e-джоба с root,
  кросс-сборка под Windows/Linux/macOS.

## Этап 5. Наблюдения и ограничения

* Смешивание транспортов в одной сети работает без специального кода:
  ретранслятор абстрагирует транспорт интерфейсом `rawConn`.
* PBKDF2 с 200 000 итераций заметно замедляет перебор пароля, но лимита
  попыток на сервере пока нет — в дорожной карте.
* На Windows создание TUN-адаптера требует Wintun; протокол и ретранслятор
  от этого не зависят (см. `docs/WINDOWS.md`).
* В песочнице исходящий интернет закрыт, поэтому NAT-тест проверяет
  доступность через отдельный network namespace, эмулирующий «интернет».
